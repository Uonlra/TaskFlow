# TaskFlow 面试问题集合与参考解答

## 1. 这个项目解决了什么问题？
参考回答：
- 核心是把个人任务管理从“记一条”升级到“可持续推进”。
- 提供任务全流程：创建、筛选、推进、复盘。
- 总览能快速识别逾期风险与完成节奏，帮助用户决定先做什么。

## 2. 为什么选择 Next.js App Router？
参考回答：
- 页面路由、布局、服务端逻辑天然一体化，组织成本低。
- 便于在 layout 层做鉴权重定向和服务端会话检查。
- 对后续部署到 Vercel 友好，工程路径更顺。

## 3. 认证流程是如何设计的？
参考回答：
- 表单侧支持注册与登录，服务端处理回调。
- 回调路由同时处理 `code exchange` 与 `OTP verify` 场景。
- middleware 每次请求触发会话刷新，保证 SSR 与客户端状态一致。

## 4. 如果 Appwrite 环境变量没配置，应用会怎么样？
参考回答：
- 自动进入演示模式，使用本地数据运行。
- 依然可以完整体验任务流程，不阻塞项目展示。
- 配好环境变量后可平滑切换到真实数据链路。

## 5. 为什么用 Zustand，而不是 Redux？
参考回答：
- 本项目状态模型相对聚焦（任务域为主），Zustand 足够且轻量。
- 使用 `persist` 可以快速实现本地持久化。
- API 简洁，减少样板代码，开发效率更高。

## 6. 任务筛选支持哪些维度？
参考回答：
- 支持 query、tag、status、priority、sort 五维筛选。
- 支持 created/updated/due/priority 多策略排序。
- 筛选逻辑与展示逻辑解耦，便于后续扩展高级查询。

## 7. URL 状态同步有什么价值？
参考回答：
- 当前筛选/排序/范围可通过链接直接分享。
- 刷新页面后状态可恢复，用户认知连续。
- 对排查问题和复现场景也有帮助。

## 8. 截止日期风险是如何判断的？
参考回答：
- 将任务抽象为 `overdue / today / upcoming / none` 四类。
- 统一输出 label、tone、sortWeight，供 UI 和排序共同消费。
- 这样可以避免“显示逻辑”和“排序逻辑”重复实现。

## 9. 总览页主要展示了哪些信息？
参考回答：
- 统计卡片：未完成、进行中、完成、逾期、今日到期、3 天内到期。
- 图表模块：完成趋势、状态分布、标签分布。
- 辅助模块：近期活动、标签摘要、即将到期任务。

## 10. 图表为什么采用轻量实现方式？
参考回答：
- 当前图表以概览为主，复杂交互需求有限。
- 采用轻量实现可控制依赖体积与复杂度。
- 后续若要支持高级交互，可平滑替换为成熟图表库。

## 11. 你如何保证表单输入质量？
参考回答：
- 使用 React Hook Form + Zod 进行声明式校验。
- 登录、注册、任务分别维护独立 schema。
- 错误信息直接落在字段级，反馈及时清晰。

## 12. 数据库层做了哪些设计？
参考回答：
- 任务数据保存在 Appwrite `tasks` table 中，并以当前用户作为归属身份。
- 每条任务创建时写入当前用户的行级权限，限制只有本人可以读写。
- 个人资料使用 Appwrite Account 的 name 与 prefs 保存，避免为了小项目额外维护 profiles 表。

## 13. 如何处理错误与用户反馈？
参考回答：
- 提供全局 Toast 机制区分成功/失败/提示。
- 关键异步流程统一 try/catch，给出可读错误信息。
- 页面层保留 loading 与 empty state，避免“空白页面”。

## 14. 登录态在前后端如何保持一致？
参考回答：
- 登录成功后服务端把 Appwrite session secret 写入 `httpOnly` cookie。
- 页面和 API 通过当前站点的服务端接口读取会话，再访问 Appwrite。
- layout 层在服务端校验用户，未登录直接重定向。

## 15. 项目中有哪些可复用组件？
参考回答：
- 认证壳组件（表单容器）可复用到登录/注册。
- 任务弹窗、确认弹窗、空状态组件在多个页面复用。
- 状态徽章、优先级徽章、页面头部等属于通用展示组件。

## 16. 如果任务量增大（例如 10w+），你会怎么改？
参考回答：
- 将筛选/排序下沉到后端查询，前端改为分页/游标加载。
- 引入数据库索引策略与按需字段返回。
- 对总览统计使用聚合接口或异步计算，减少前端全量扫描。

## 17. 这个项目里你最看重的工程实践是什么？
参考回答：
- 双模式运行（演示/真实）提升可交付性。
- 业务规则函数化（截止风险、排序、标签解析）提升可维护性。
- 类型约束与校验前置，减少运行期错误。

## 18. 如果未来要做共享任务，你会怎么扩展？
参考回答：
- 数据层新增共享关系、评论、活动日志等表。
- 权限从“仅本人”扩展到“被分享成员可见/可编辑”。
- 前端增加分享对象选择、评论流、变更历史与通知。

## 19. 这个项目你遇到的主要挑战是什么？
参考回答：
- 需要在“可演示性”和“真实数据链路”之间平衡。
- 解决方式是通过统一 store 接口屏蔽数据源差异。
- 同时在路由层和中间件层补齐鉴权，保证行为一致。

## 20. 你如何继续迭代这个项目？
参考回答：
- 增加自动化测试（schema、store、关键交互）。
- 增加附件上传、子任务、任务评论和提醒通知。
- 补充必要的错误记录与性能观察，让长期维护更踏实。

## 使用建议
- 回答时先说“背景-方案-结果”，每题控制在 30-90 秒。
- 尽量结合你实际改动过的模块，不背模板答案。
- 对不确定的问题，优先说权衡过程和下一步方案。
