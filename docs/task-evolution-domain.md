# 任务演进领域约定

## 实施状态

已实现命令校验、纯状态转换、摘要计算和领域测试，并已接入持久化与任务详情操作。详情流程见 [任务详情操作说明](./task-evolution-detail.md)，存储现状及部署步骤见 [持久化与同步](./task-evolution-persistence.md)。云端仍待目标环境迁移和真实账户验收。

## 数据边界

一个 `TaskEvolution` 对应一个现有主任务，通过 `taskId` 关联。它包含当前目标、目标版本、探索分支、执行步骤、成果、采纳记录和演进事件。

探索分支和执行步骤不会作为普通 `Task` 插入全局列表，因此不会直接增加任务、日历或总览的完成统计。转为独立任务后才成为新的统计对象。

目标包含 `objective`（目标）和 `successCriteria`（完成标准）。现有 `description` 继续承载背景信息，不自动当作完成标准。首次为旧任务建立演进数据时，以现有标题作为初始目标，完成标准留空，记录采集时点的 `baseline`。旧任务既有状态保持不变，不从更新时间补造历史。

分支的 `baseGoalVersion` 永久指向创建时的目标版本，`reviewedGoalVersion` 表示最近确认适用的版本。版本对应事件中的目标快照。目标实际变化时递增版本；普通进展和不改变目标的采纳只递增整体修订号。

## 命令与记录

所有操作通过 `taskEvolutionCommandSchema` 校验，携带稳定的 `operationId` 和 `expectedRevision`。操作时间由调用端的可信存储层提供，不由表单决定。

`applyTaskEvolutionCommand` 只返回新状态，失败不修改输入对象。一个转换同时包含目标修改和对应事件，便于仓储在一次提交中保存。它自身不是数据库事务。

| 命令                         | 行为                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| `create_branch`              | 从当前目标创建一条平行探索，创建事件也是图中的分叉起点     |
| `add_step` / `set_step_done` | 维护分支内的执行步骤，不产生额外探索层级                   |
| `record_progress`            | 记录主线或指定分支的普通进展，不自动生成待采纳成果         |
| `submit_result`              | 显式提交不可变的成果版本，包含可以分别选择的成果条目       |
| `adopt_result`               | 采纳指定版本中的部分条目，同时保存确认后的主目标与前后快照 |
| `adjust_goal`                | 正式调整目标或完成标准，必须说明原因                       |
| `review_branch`              | 确认分支对当前目标仍适用，保存原因及确认版本               |
| `set_branch_status`          | 待探索、探索中、已结束、已搁置之间显式切换                 |
| `withdraw_adoption`          | 撤回指定采纳，显式传入确认后的目标，保留原始采纳与撤回事件 |
| `complete` / `reopen`        | 按当前标准验收或重新打开主任务                             |

分支搁置、结束与成果采纳是不同事实，不能仅根据状态变化绘制汇入线。采纳后分支状态不变。目标变化后，来源分支也需要检查；不自动代表用户确认它仍然适用。

同一成果可以多次采纳不同条目，仍生效的采纳不能重复包含同一条目。撤回后可以重新采纳。后续提交新成果不会改写已有成果或采纳快照。

完成主任务前必须有完成标准，且分支已经结束、搁置或转出。已完成任务要先重新打开才能继续修改。具体的跨任务“转为独立任务”需要仓储事务，尚未由纯转换函数实现。

## 幂等与冲突

相同操作 ID 和规范化后相同命令再次提交时，返回当前状态，不追加事件；即使期间又有进展，也不能重复执行原操作。相同 ID 携带不同内容应报告冲突。

新命令的 `expectedRevision` 必须与读取到的当前修订号一致。存储层必须在提交时再次执行版本比较，以防两个客户端同时读取同一版本后均通过内存检查。

撤回必须显式提交用户确认的目标，并基于最新修订号保存，不能直接用历史快照覆盖后续修改。历史采纳的 `beforeGoal` 和 `afterGoal` 不可重写。

## 仓储接入要求

1. 从当前账户权限范围内加载主任务和演进数据，校验持久化版本及完整性。
2. 首次初始化必须读取真实主任务，旧的已完成或删除状态不能被客户端覆盖。
3. 应用命令后，将主任务投影、演进数据、事件及必要同步队列作为一次一致性提交保存；初始化也要防止并发创建。
4. 使用原始修订号进行条件写入；条件不满足时重新加载并反馈冲突。
5. 云端必须先核对实际版本支持的事务及条件更新能力，再决定表结构；不能用前端依次调用两个更新接口冒充原子保存。
6. SQLite 使用数据库事务；浏览器存储若无法持久化，必须明确报告失败，不能宣称记录已安全保存。
7. 重试与同步保留原始操作 ID，重复推送不能重复产生采纳或历史事件。
8. 服务端完成及修改接口也必须执行新规则，不能仅在新增界面限制旧操作入口。

## 摘要和演进图

`getTaskExplorationSummary` 只将明确提交且仍有未采纳条目的成果计入待决策数。搁置分支和待检查分支暂不计入待采纳提示；待检查数量单独展示。这里的待采纳数量是成果版本数，不是分支数。

每个事件具有连续的 `revision`，同一时间产生的事件按修订号排序。时间用于显示，不承担拓扑关系。图中通过分支创建事件和采纳引用建立连线，折叠后仍应保留连接提示。

## 下一阶段的迁移与关系规则

- 浏览器、SQLite 与云端各自增加存储版本和升级步骤，原任务字段与 ID 保持可读。
- 导出采用新版格式保留 ID、关系、成果快照和演进；导入先完整校验并统一重映射 ID，再保存。旧格式按无演进历史的任务导入。
- 复制任务默认复制当前目标和完成标准，创建新的任务与起点，不复制历史采纳事实。
- 删除主任务时将整个演进数据纳入同一删除/恢复策略，不对正常的领域记录逐条硬删除。
- 转为独立任务时，原分支留下转出记录和新任务引用，新任务建立可追溯的来源；两侧写入必须原子完成。
- 尚未实现的数据功能不能通过界面或导出入口静默丢弃演进内容。
